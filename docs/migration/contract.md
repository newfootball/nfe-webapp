The prototype [#45](https://github.com/newfootball/nfe-webapp/issues/45) remains blocked until #44's contract is actually validated. No production action is authorized by this document.

## Decisions and evidence

**Authorized by [#43](https://github.com/newfootball/nfe-webapp/issues/43) and #44:** build TanStack Start in isolated preproduction, use self-hosted Appwrite for authentication and business data and managed Backblaze B2 for media, then make one production cutover. Next.js remains authoritative until cutover. There is exactly one production write authority at any time; no implicit dual writes. Preserve public IDs, URLs, business dates, permissions and FR/EN behavior. Bun, React, Tailwind v4 and shadcn/ui remain; pin versions after the prototype. Browser transfers use short-lived S3 presigned URLs by default, with private buckets and Start authorizing each operation. Appwrite stores business permissions and media metadata, not expiring URLs.

**Observable at base `7b284f689493badafc37231348ee01f975321c2f`:** `prisma/schema.prisma` has User, Account and Session; Account has provider/account IDs and an optional password, while User also has an optional password. `src/lib/auth.ts` uses better-auth with Prisma, optional Google and custom password functions; `src/lib/password.ts` uses bcryptjs with cost 10 for newly generated hashes. Actual historical hash formats, which password field is authoritative per account, data volumes, current production configuration and provider identities require inspection on a protected representative export. Cloudinary direct upload and image transformation code exists; this alone does not establish the complete production media pipeline.

**Not yet known or approved:** all values below, compatibility of the selected self-hosted versions, and proof of restoration, reverse import, performance and parity. Do not infer production facts from the repository or from Appwrite Cloud documentation.

## Migration protocol and write authority

Record a run ID, operator, timestamps, source and destination versions, checkpoints, checksums, counts, exceptions and sign-offs in an access-controlled runbook. Keep exports, passwords, tokens and signed URLs out of Git and public reports. Rehearse the entire procedure on an isolated representative copy, including a post-reopening rollback, within the approved freeze and recovery limits before scheduling production.

| Phase | Production write authority | Required action and exit evidence |
| --- | --- | --- |
| Prepare and initial import | Next / PostgreSQL and current media | Inventory every write path and background worker; take a consistent snapshot and checkpoint. Import identities, data and actual media into isolated target using deterministic IDs and idempotent upserts. Record source manifests, object versions and fingerprints. Continue serving and writing only on Next. |
| Freeze and final import | None | Announce maintenance; enforce server-side rejection of all mutations, registrations, login/session creation, password resets, OAuth linking, admin jobs, webhooks and background writes. Stop workers and ingress capable of writes, drain in-flight requests, direct uploads and multipart completions, and revoke or wait out outstanding write URLs before the final snapshot. Verify zero accepted writes at every entry point; stop if fencing cannot be proven. |
| Reconcile and switch | None | Take a consistent final snapshot/checkpoint. Apply changes since initial import **including deletions** via a proven complete change journal/tombstones, or compare complete final inventories and remove target-only records and objects. Never rely on `updatedAt` alone to detect deletions. Re-run until reconciliation passes, then switch routing to the target while still fenced. |
| Reopen | Start / Appwrite and B2 | After signed go decision and target read-only smoke tests, enable target writes only. Keep Next fenced, including direct access, jobs and credentials. Record the precise authority transition and capture all target writes/deletions for reverse migration. Monitor against approved thresholds using the runbook; no automatic second writer. |

A direct-upload URL is an outstanding write capability even if the application is in maintenance. The runbook must inventory its maximum expiry, abort or finish multipart uploads, and prove B2 cannot accept old capabilities before the final manifest. Equivalent fencing applies on rollback. Failure to fence or enumerate writes is a no-go.

## Identity and media invariants

- Maintain a durable, one-to-one mapping between legacy public user IDs and target auth/business IDs; preserve all references and dates. Check uniqueness and referential integrity, including accounts without email. Resolve collisions explicitly; never silently merge users.
- Inventory credential accounts and hashes from both possible fields, including prefixes and costs, and prove precedence and self-hosted import/verification on representative hashes. Test correct and incorrect passwords and subsequent password changes. If compatibility cannot be proven, use an approved secure reset flow before enabling affected accounts; never copy plaintext passwords or silently discard credentials. Treat hashes and mappings as sensitive.
- Do not transfer better-auth sessions or reset tokens. Invalidate old sessions and require sign-in again; test email/password, reset and Google in FR/EN. Match Google identities by verified provider subject (`sub`), not email alone; prevent duplicate or accidental linking and test existing Google-only and linked accounts. Verify actual provider identity mapping, callback configuration and linking behavior on the pinned self-hosted version. Google documents `sub` as the stable identifier: [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).
- Copy original media bytes and all required derived assets; inventory Cloudinary transformations, video processing, thumbnails, access and external URLs before deciding replacements. Verify each object by size and a strong content digest, not merely URL or multipart ETag. Record provider, bucket, key, version where applicable, size, MIME type, digest, owner and business status. Handle missing originals or transformations as explicit blocking exceptions. Preserve old media until rollback and retention gates pass.
- Start checks identity, ownership, status and operation before issuing a narrowly scoped, short-lived signature; validate size/type and uploaded object before publishing metadata. Prevent overwrite and unauthorized access, clean abandoned multipart uploads, and test CORS, expiry, multipart and range playback on the selected B2 configuration. Appwrite ACLs do not enforce B2 access. Backblaze documents [S3-compatible presigned uploads and downloads](https://help.backblaze.com/hc/en-us/articles/360047425453-Getting-Started-with-the-S3-Compatible-API), [CORS](https://www.backblaze.com/docs/cloud-storage-cross-origin-resource-sharing-rules) and [multipart upload](https://www.backblaze.com/apidocs/s3-create-multipart-upload); these do not prove the application integration.

## Reconciliation and go/no-go

Compare the same frozen checkpoint on both sides, by entity and relationship: counts, IDs, canonical field values and business dates, foreign references, permissions, deletion sets and duplicate/collision reports. Compare media manifests and actual bytes, including access and required derivatives. Produce protected detailed discrepancy reports and a redacted summary. Acceptance: **zero unexplained missing, extra, mismatched or orphaned records or media**, zero unauthorized access successes, and zero unaccounted deletions. An explicitly approved exception must identify affected records, remediation and owner; no exception may conceal lost accepted writes or security failures.

Before reopening writes, the accountable approver records a go only if all are true:

1. Complete FR/EN route, status, redirect, API, rights and integration parity evidence passes or approved exceptions are recorded; critical journeys and Google/password recovery work.
2. Initial and final imports are repeatable; frozen reconciliation satisfies the rules above, including real files and deletions; every failed item is resolved.
3. A representative rehearsal proves freeze and recovery within the approved maintenance, RPO and RTO values; restore and post-reopening reverse migration are tested. Backups and manifests are restorable and accessible to named operators.
4. Measured critical-journey p50/p95 and sample sizes meet the approved numeric budgets; capacity, maximum video, costs and monitoring are validated.
5. Both write fences, OAuth callbacks, secrets, private object authorization, uploads, deletion propagation and rollback runbook have passed; the target version and config are pinned and recorded.

Any missing value, failed check, unexplained discrepancy or absent sign-off means **no-go**. Remain frozen and execute the appropriate rollback; if the approved freeze window is threatened, stop rather than extend it implicitly.

## Rollback and retirement

**Before target writes reopen:** keep both sides fenced; route back to Next, verify the last authoritative PostgreSQL and media state and restore configuration, jobs and access. Reconcile against the final legacy checkpoint, smoke-test reads and authentication, then explicitly reopen only Next writes. Discard or quarantine target imports only after evidence and retention requirements are satisfied.

**After target writes reopen:** a route switch or old snapshot restore alone loses accepted target writes and is forbidden. First fence and drain all target writers, jobs, sessions, presigned uploads and multipart completions; verify no further writes and snapshot Appwrite and B2. Export a complete target delta since the cutover checkpoint, including creations, updates, deletions, ownership/permissions, new accounts, linked Google identities, password resets and changes, and B2 objects and versions. Apply a tested, idempotent reverse mapping/import to the fenced legacy system, copying actual B2 bytes to a legacy-readable durable location and restoring required processing and references. Reconcile target snapshot against the resulting legacy state with the same zero-loss rules, including deletion propagation and digest verification. Verify new accounts can authenticate and changed passwords remain effective; if hashes cannot be safely imported, execute a previously approved secure reset path that preserves account access, and verify it before reopening. Invalidate target sessions and require reconnect. Smoke-test authorized/unauthorized access, media and critical journeys, record sign-off, switch routing and reopen only Next. Keep target snapshots and manifests protected for reconciliation and retention. If reverse import, credentials or media cannot be proven, **stay frozen** and repair forward or restore a verified target snapshot; never reopen stale Next. The reverse procedure and its duration must be rehearsed before any target writes are allowed.

Retain the legacy application, database, media, configuration and recoverable backups for the approved period, with restricted access and tested restoration; keep them fenced while target is authoritative. After the period, #67 requires signed confirmation of reconciliation, recovery, legal deletion, archive restoration and owner approval before disabling and securely deleting legacy resources. Record what was retained, destroyed and when; no retention duration is assumed here.
